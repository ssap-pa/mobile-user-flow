# Mobile User Flow

사용자가 앱에서 이루려는 일을 중심으로 진입부터 완료·복귀까지 연결한다. 토스의 관찰된 동선에서 추출한 원칙을 사용하되, 사용자의 업종·브랜드·기존 구조에 맞춰 선택한다. Mobile MCP나 토스 접속은 필요하지 않다.

## 참고 자료 선택

- 새로운 업종에 적용할 때는 [패턴 선택표](references/patterns.md)를 읽는다.
- 토스의 실제 경로나 근거를 요청받으면 [토스 실측 범위](references/toss-observations.md)를 읽는다. 확인한 경로까지만 관찰로 설명하고, 그 이후의 인증·완료·오류 처리는 설계 제안으로 표시한다.
- 화면과 구현 작업을 구체화할 때는 [동선 명세 형식](references/flow-spec.md)을 사용한다. 간단한 변경에는 영향받는 부분만 작성한다.

## 1. 먼저 결정할 것

- 기존 프로젝트·요구사항에서 대상 사용자, 가장 자주 하는 일, 가장 중요한 완료 결과, 사용 환경, 기존 내비게이션과 디자인 시스템을 파악한다.
- 핵심 작업을 “사용자가 [상황]에서 [대상]을 [행동]하여 [결과]를 얻는다”로 적는다. 우선순위가 가장 높은 작업부터 설계한다.
- 정보가 부족해도 되돌릴 수 있는 선택은 가정을 밝히고 진행한다. 사용자 역할이나 실제 업무 규칙처럼 결과를 바꾸는 누락 정보만 질문한다.
- 기획 요청이면 동선·화면 명세를 만든다. 구현 요청이면 명세를 필요한 만큼 정리한 뒤 구현과 검증까지 진행한다. 요청하지 않은 중간 승인 단계를 만들지 않는다.

## 2. 정보 구조를 작업 빈도로 정리한다

- 홈에는 현재 상태, 지금 할 핵심 작업, 이어서 할 일 또는 최근 항목을 우선 배치한다. 보여줄 상태가 없는 단일 목적 앱은 작업 화면 자체를 시작점으로 삼을 수 있다.
- 전역 내비게이션은 반복 방문하는 독립 목적에 배정한다. 탭 개수·명칭을 토스에서 가져오지 않는다. 단일 작업에는 불필요한 탭을 추가하지 않는다.
- 기능이 많을 때만 검색·분류·최근 이용을 갖춘 전체 서비스 목록을 둔다. 설정과 드물게 쓰는 기능 때문에 주요 탭을 늘리지 않는다.
- 독립된 하위 서비스가 여러 화면을 가질 때만 내부 내비게이션을 둔다. 상위 앱으로 돌아가는 경로와 현재 영역을 드러낸다.
- [패턴 선택표](references/patterns.md)를 읽고 적용할 패턴과 적용 이유를 정한다. 혜택·쇼핑·피드·프로필은 도메인에 필요할 때만 포함한다.

## 3. 핵심 동선을 끝까지 연결한다

각 작업에 진입 → 대상 선택/탐색 → 필요한 정보 입력 → 실행 → 결과 → 다음 행동/복귀를 매핑한다. 작업에 불필요한 단계는 생략한다.

- 탐색형 작업은 요약 → 필터 가능한 목록 → 상세 → 맥락에 맞는 행동으로 구성한다. 검색어·필터·목록 위치를 뒤로 가기 이후에도 복원한다.
- 입력 방법이 실제로 다르면 초기에 분기한다. 예: 직접 입력/최근 대상/검색/스캔. 같은 결과로 합류하는 지점을 정의한다.
- 다음 판단에 필요한 정보만 순서대로 받는다. 짧고 밀접한 입력은 묶고, 독립된 판단이나 복잡한 입력은 분리한다. 한 필드마다 무조건 화면을 만들지 않는다.
- 최근 항목·즐겨찾기·기존 값은 반복 작업을 줄이는 데 사용한다. 개인정보를 드러내거나 잘못된 대상을 자동 확정하지 않는다.
- 선택지가 짧고 현재 작업에 종속되면 시트/팝오버를 사용한다. 검색·긴 입력·별도 주소가 필요한 상세는 전체 화면을 우선한다. 시트 중첩을 피한다.
- 완료에 필요한 주 행동을 명확히 한다. 긴 상세에서는 고정 CTA를 고려하고, 키보드·안전 영역·본문 마지막 항목을 가리지 않게 한다.
- 버튼은 “다음”보다 가능한 경우 “시간 선택”, “예약 확정”처럼 결과를 설명한다. 단순 조회·저장은 불필요한 확인을 추가하지 않는다. 결제·공개 게시·삭제처럼 영향이 큰 실행은 대상과 결과를 확인할 수 있게 한다.
- 가입·프로필·권한은 해당 기능에 필요해지는 지점에서 요청한다. 거절·건너뛰기 후 가능한 경로와 입력 보존을 정의한다. 실제 업무상 필수 조건은 우회시키지 않는다.
- 완료 화면에는 결과 상태, 식별 가능한 요약, 다음 행동을 둔다. 접수/처리 중/완료를 구분하고 실패를 성공처럼 표시하지 않는다.

## 4. 화면과 상태를 함께 설계한다

[동선 명세 형식](references/flow-spec.md)을 사용하되 작업 크기에 맞게 줄인다. 모든 버튼에 목적지나 상태 변화가 있어야 한다.

- 각 화면에 사용자 목적, 진입점, 정보 우선순위, 주 행동, 보조 행동, 뒤로/닫기 결과를 정의한다.
- 관련 있는 빈 상태·로딩·검증 오류·실패·권한 거절·세션 만료를 포함한다. 네트워크 작업은 지연·재시도·중복 제출을 고려한다. 오프라인 작업이 필요하면 임시 저장과 동기화 상태를 정의한다.
- 빈 상태에는 비어 있는 이유와 가능한 첫 행동을 준다. 오류는 기존 입력을 보존하고 문제 위치와 회복 방법을 제시한다.
- 모바일 웹은 브라우저 뒤로 가기·새로고침·직접 URL 진입을, 네이티브 앱은 시스템 뒤로 가기·재진입을 고려한다. 지원 플랫폼에 해당하는 것만 적용한다.
- 터치 조작, 읽기 순서, 입력 라벨, 포커스, 글자 확대, 키보드 노출을 확인한다. 아이콘만으로 중요한 행동을 구분하지 않는다.

## 5. 구현과 검증

- 기존 기술·라우팅·컴포넌트·디자인 시스템을 존중한다. 이 스킬 자체가 특정 프레임워크, 색상, 카드 스타일을 요구하지 않는다.
- 구현 요청에서는 화면을 연결하고 실제 상태 전이를 만든다. 서버가 없으면 모의 데이터/동작임을 구분하며 실제 완료라고 표현하지 않는다.
- 핵심 정상 경로 하나를 진입부터 결과까지 확인하고, 그 경로의 중요한 실패·복귀 경로를 확인한다. 변경 범위와 위험에 비례해 검증한다.
- 상세에서 돌아왔을 때 맥락 유지, 입력 중 취소, 재시도 시 중복 발생 여부, 고정 버튼과 키보드 충돌을 관련 화면에서 확인한다.
- 외부 실제 앱을 조사하는 경우 화면 전환 뒤 새 상태를 확인한 후 다음 행동을 정한다. 지연 화면을 가정한 연속 좌표 클릭을 하지 않는다. 탐색 요청을 가입·결제·게시 실행 허가로 해석하지 않는다.
- 최종 답변은 적용한 동선과 이유, 구현/기획 결과, 실제 검증 범위와 미확인 사항을 간결하게 전달한다. 관찰·추론·새 설계 제안을 구분한다.

## 기준

토스 실측은 패턴의 출처이며 모든 업종에 대한 효과 검증이 아니다. 하단 탭 다섯 개, 보상 미션, 금융 용어, 계정 생성, 토스의 시각 디자인을 기본값으로 복제하지 않는다. 작업 완료에 필요한 최소 구조를 선택한다.
